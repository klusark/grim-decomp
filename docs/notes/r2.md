# Round r2: the last assembled functions of GRIMFANDANGO.EXE and LUA.DLL (2026-11-09)

Scope: the 21 functions of GRIMFANDANGO.EXE and LUA.DLL that were still built from the original machine code
(`src/<PROG>/asm_funcs.s`) at 85dd22f and are not ordinary code paths: `_ftol`, `__chkstk`, eleven SEH / C++ unwind
funclets of the EXE, the dead loop tail FUN_0042003c, seven C++ unwind funclets of LUA.DLL.  After this round
`names/asm_funcs.json` lists nothing for GRIMFANDANGO.EXE, LUA.DLL and CHORE.DLL (IMUSE.DLL: round r1).

Method: for every function, who can still reach it in the linked rebuild (objects, instructions, data image), what
reached it in the original (scope tables / FuncInfo records, their parents and what those parents call inside the
protected regions), then: dead -> `names/lib_replace.json` "dead" (build_src.py keeps the C text under `#if 0`, the
remaining data-image references resolve to link.py's trap stubs: `__builtin_trap`, ud2); a register-ABI runtime helper
with an equivalent in the toolchain -> that equivalent, with a differential test against the original machine code.

## Could anything still unwind through the parents?

* **C++ throw**: neither the EXE nor LUA.DLL contains `_CxxThrowException`; the only `RaiseException` call of each
  is the runtime's floating-point `_raise_exc` (not in the rebuild). The game never throws.
* **longjmp** (Lua errors: `lua_error` -> msvcrt `longjmp` to the `_setjmp3` buffer of luaD_protectedrun): MSVC's
  longjmp unwinds the registered frames between, and `__CxxFrameHandler` would run the funclets of a parent that is in
  a protected state. The protected regions are only the constructor call after a `new`: in LUA.DLL `lvm__ddb0` (four
  stores, cannot raise) and `lstate__75e0` (stores and one call of the host allocator through the service table, which
  does not enter Lua); in the EXE Walker_Create, the Primitive / ObjectState / Sector constructors, StateImage_Init ->
  Resource_Load: none enters Lua. So the funclets could not run in the original either, except for a hardware
  exception inside a constructor caught by an outer `__except` that unwinds (none exists outside the runtime).
* **SEH frames in the rebuild**: the gcc code registers none, with one exception: the compiled ObjectState_Construct
  (objstate.c) still links an fs:[0] record (the `seh_strip` rule of build_src.py, which `names/seh_strip_logic.json`
  asks for, does not match it: its variables are frame_locals `#define`s and the state update is a `CONCAT31`). Its
  handler was the compiled C of the thunk FUN_004d60e9, `__CxxFrameHandler()` without the FuncInfo in EAX, which would
  have crashed on any exception or longjmp unwind through the constructor. `build/overrides_r2.c` makes FUN_004d60e9 a
  valid handler that returns ExceptionContinueSearch (the frame is inert). The other five EXE thunks (FUN_004d6046,
  605b, 607b, 60ba, 610b) and the LUA.DLL thunks are not registered by anything (Actor_CreateWalker only stores
  FUN_004d605b in a local); left as they are.
* `build/difftest/r2/reach.py` prints all of this for the linked build (objects referencing each removed symbol: only
  `data_s.o`; instructions naming them: 0; references to each scope table / FuncInfo record: none; fs: accesses:
  mingw's start-up and ObjectState_Construct in the EXE, mingw's `_CRT_INIT` TIB reads in LUA.DLL).
* The C++ unwind map of PrimitiveList_Append has a second funclet at 0x004d603b that Ghidra never made a function; the
  data image keeps its original value (`.long 0x004d603b`, "code address, not a function start").

## Differential tests (build/difftest/r2)

`build.sh [ftol cases] [chkstk cases] [traced cases] [thread sizes]` slices `_ftol` and `FUN_004addf0` from
`git show 85dd22f:src/GRIMFANDANGO.EXE/asm_funcs.s` (renamed `orig_*`) and links them next to what the rebuilt exe's
symbols resolve to now: `__ftol` from `libmsvcrt.a` and `_FUN_004addf0` of build/overrides_r2.c compiled with link.py's
flags. `harness.S` sets up the registers / x87 state and records everything after the call.

* `ftol_test`: 4,000,000 cases, 0 differences. Every rounding mode and precision control (plus the infinity-control
  and reserved bits), x87 depth 0 / 1 / 7 below the value; values: random 80-bit patterns (pseudo-denormals,
  unnormals, pseudo-NaN), integers +- ulps, halves, +-2^31 / 2^32 / 2^52 / 2^53 / 2^62 / 2^63 / 2^64 +- ulps, +-0,
  +-inf, quiet / signalling NaNs, denormals, huge exponents, doubles and floats from random bits. Compared: EAX EDX ECX
  EBX ESI EDI EBP, ESP balance, CW / SW / TW after the call, the registers left on the stack; the original is also
  checked against gcc's truncation for every finite in-range value (2,717,413) and gives 0x8000000000000000 with IE
  for invalid ones (1,261,579). (Unmasked x87 exceptions are not tested: both trap on the same instruction.)
* `chkstk_test`: part 1, 1,000,000 sizes (around every page multiple +-8, random up to 32 MiB) on a private committed
  stack with the TIB limits pointed at it: ECX EDX EBX ESI EDI EBP and ESP after the call and the stack memory around
  the old and new top: 0 differences. EAX differs in every case, as expected (original: the return address; libgcc:
  the old ESP; EAX is scratch for `__chkstk` callers). Part 2, 20,000 sizes traced with the trap flag (a vectored
  handler records ECX at each probe instruction; it stops before `mov esp, ecx`): 321,446 probes, 0 differences in the probe sequence. The original probes the last page twice when the size is
  a non-zero multiple of 4 KiB (merged before comparing); libgcc probes with `or dword [ecx], 0` (stores the unchanged
  value) where the original reads. Part 3, 300 sizes up to 12 MiB on fresh 16 MiB-reserve thread stacks (guard-page
  growth, then the whole block is written from its low end), both versions: 0 failures.
  Observed while writing the tracer: for sizes below 8 both versions read the saved ECX and the return address from
  below the new ESP (an asynchronous write to the stack there, such as an exception frame, would clobber them); not a
  difference, and no code calls it with such sizes.
* `mutate.sh`: 8 of 8 mutations of the original caught (rounding mode, control word not restored, value left on the
  x87 stack, EDX dropped, 8 KiB probe stride, ECX not restored, no probe in the loop, page loop skipped; the last three
  also crash part 3, as a skipped guard page does). `MUT=1` (original against itself): 0 differences.

## The data image: false and missed pointers (separate commit)

FUN_0042003c's only reference was not a reference: build/gendata.py turns every aligned dword of .rdata / .data whose
value is a function start or an address inside the data sections into a relocation, and the VIMA / IMA ADPCM step table
0x004daa58 (89 16-bit entries, used by the Smush audio decoder FUN_004cbf50 through FUN_004cbc00, the
`LECMODULE insane_wave flobdec` codec) contains the pairs 60, 66 = 0x0042003c (FUN_0042003c's address) and 73, 80 /
88, 97 / 107, 118 / 130, 143, which look like .data addresses. In the rebuilt exe these ten entries held relocated
addresses (0x004ca240 ...), so the decoder's step sizes for indices 22-31 and the table DAT_008d7868 it derives from
them were wrong.

`build/difftest/r2/relocheck.py <original PE> <data.s> <sections.json>` compares data.s with the base relocation table
of the original program (its .reloc lists every absolute address the linker emitted, so it is the ground truth):
GRIMFANDANGO.EXE 1886 original relocations in .rdata/.data, 24 false pointers in data.s, 86 missed; LUA.DLL 0 false, 68
missed; CHORE.DLL 0 / 0; IMUSE.DLL 1 false (0x100153c4, `_sect_data + 0x9600`; not changed here, IMUSE.DLL is round r1's).
The 24 false EXE pointers: the step table (5 dwords), glyph bits of the built-in font table UINT_004eca04 that
Text_WrapLines uses (0x004ecd40, 0x004ecf08), and tables of the runtime / deflate. Missed: 4 real data pointers whose
bytes look like text (the subsystem-name strings of PTR_sputControl_Initialize_004e7e00), the other 82 (and LUA.DLL's
68) are code addresses that are not function starts, all inside runtime code that is not in the rebuild.
`names/data_relocs.json` (new, read by gendata.py) lists the EXE's 24 `not_pointers` and 4 `pointers`.
