# Round s2: IMUSE.DLL's music-stream difference and false pointer (2026-11-09)

Base: main at 6da2d60 (no function built from assembly, cleanroom 5107 of 5107).  Two problems from round r:

1. agent r1's gdb scenario 3: after `ImSetState(1000)` and 250 frames the original IMUSE.DLL still finds the fading music
   stream at `ImSetState(1001)` (and fades it back in), the rebuilt one finds none and starts it again (57 against 62 calls).
2. a false pointer in IMUSE.DLL's data image at 0x100153c4 (agent r2's `relocheck.py`); LUA.DLL / CHORE.DLL to check.

Result: **(1) is not a difference of the code but of the time base of the test**; no function differs (trace and
differential test below), nothing to fix in the C.  **(2) fixed** (`names/data_relocs.json`): IMUSE.DLL's data image now
has the original's relocations exactly; CHORE.DLL has none wrong; LUA.DLL's 68 missed relocations are confirmed to be code
addresses in jump tables of dead runtime code.  Cleanroom: see the end.

## 1. The music stream at ImSetState(1001): the time base

r1 ran every build with `GRIM_SIMTIME=17` (ftrun.sh).  Under GRIM_SIMTIME the **rebuilt** IMUSE.DLL runs on game time
(build/overrides.c, "GRIM_SIMTIME: iMUSE in game time": no timer thread, the EXE calls `GRIM_ImSimStep(17)` every frame,
one heartbeat per 20 ms of game time), but the **original** DLL has no `GRIM_ImSimStep` export, so `GRIM_lua_cmd_poll`
finds nothing and the original keeps its WINMM timer thread: heartbeats every 20 ms of *real* time, while the frames run at
~300 per second under gdb.  `ImSetState(1000)` does `ImFadeParam(0x2711, 0x600, 0, 0x78)`: Im_FadeParamImpl makes that
`0x78 * 5 / 6 = 100` fade steps, one per heartbeat (Im_FadesHeartbeat), the last one (volume 0) calls ImStopSound.  250
frames are 212 heartbeats of game time (fade over, stream gone: the 62-call trace) but only 25-40 heartbeats of real time
(fade at a quarter, stream still there: the 57-call trace).

Measured with `build/difftest/s2/s2run.sh` + `s2trace.py` (gdb; r1's frametrace.py plus, at each ImSetState, the wall
time, the frame number (GRIM_lua_cmd_poll calls) and the heartbeat number (Im_FadesHeartbeat calls), and every
ImStopSound).  Original = `C:\GOG Games\GRIMDATA\IMUSE.DLL.unpatched` (see the note below) next to the rebuilt EXE / LUA /
CHORE; rebuilt = this build.  Calls = the iMUSE calls FUN_100068b0 makes (r1's list).

`GRIM_IMUSE_REALTIME=1` (`ENVX=GRIM_IMUSE_REALTIME=1 s2run.sh ...`) or leave GRIM_SIMTIME unset; real-time runs are not
repeatable to the heartbeat, so compare call lists, not PCM, in that mode.

### Differential test of the fade engine

The functions that decide when the stream is gone (Im_FadeParamImpl 0x10003b40, Im_FadesClearSound 0x10003c70,
Im_FadesHeartbeat 0x10003cb0; compiled from the decompiled C) against the original machine code:
`build/difftest/s2/build.sh` links `build/obj/IMUSE.DLL/imuse.o` (the object in the rebuilt DLL) with the three functions
sliced from the all-assembly IMUSE.DLL (`git show 68b8b5b^:src/IMUSE.DLL/asm_funcs.s`, `build/mixdiff/slice_orig.py`,
`orig_*`) and the original data image; `fade_test.c` gives both the same random fade table (16 slots, active and stale
entries, random counters / durations / remainders / signs) and parameter model, then a random sequence of up to 64
ImFadeParam (the four fade parameters and invalid ones, durations 0..300, 0x3c, 0x78, negative, up to 0x10000000 with the
`* 5` wrap; targets 0, 0x7f, around 0x80000000, negative, random) / clear (one parameter or -1) / heartbeat steps, and
compares every return value, every ImGetParam / ImSetParam / ImStopSound call with its step number, and the table and
flag after every step.

```
bash build/difftest/s2/build.sh && build/difftest/s2/out/fade_test.exe 1000000 2
cases 1000000: 9760597 ImFadeParam, 19501747 heartbeats, 19918930 ImSetParam and 103093 ImStopSound calls from the fades (original)
0 differences
bash build/difftest/s2/mutate.sh 20000     8 of 8 mutations of the original caught (step divisor 5 -> 4, unsigned -> signed
    remainder compare, the 5/6 multiplier, the sign setge -> setg, 0x600 -> 0x700 at the stop, clear-all -1 -> -2,
    duration < 0 -> <= 0, counter jnz -> jns)
```

(The INT_MIN / -1 case of the step division, duration 858993458, traps alike in both and is not generated.)

### The game folder's IMUSE.DLL is patched

`C:\GOG Games\GRIMDATA\IMUSE.DLL` is not the shipped file: 19 bytes at 0x10004f50 / 0x10004f60 (Im_GuardEnter /
Im_GuardLeave: `lock inc` / `lock dec` + undo when negative instead of `inc` / test-and-`dec`) and one more .reloc entry
(file offset 0x2134c) differ from `IMUSE.DLL.unpatched` beside it, which is byte for byte what `raw/IMUSE.DLL/sections` holds
(same timestamp 0x3625fb9b).  The rebuilt Im_GuardLeave (build/overrides.c, `lock cmpxchg`) follows the patched variant's
idea.  I used the unpatched file as the original (r1 used the patched one; both give the same 57 calls); relocheck must be
run on the unpatched file (the patch adds a relocation in .text only, so for .rdata / .data both give the same answer).

## 2. The data image: IMUSE.DLL, LUA.DLL, CHORE.DLL against the original relocations

`build/difftest/r2/relocheck.py <original> build/obj/<PROG>/data.s raw/<PROG>/sections.json`, before:

| program | original relocations in .rdata/.data | false pointers | missed |
|---|---|---|---|
| IMUSE.DLL (unpatched file) | 267 | 1 (0x100153c4) | 0 |
| CHORE.DLL | 259 | 0 | 0 |
| LUA.DLL | 690 | 0 | 68 |

**IMUSE.DLL 0x100153c4**: bytes 0x0c..0x0f of MSVC's printf class / state table `__lookuptable` at 0x100153b8 (the
classes of `,` `-` `.` `/` = 00 06 02 10, which read as the .data address 0x10020600).  gendata.py turned them into
`.long _sect_data + 0x9600`, so the rebuilt table held an address of the rebuilt DLL there (0x6b363610 in the linked
image).  Who reads the table (`build/difftest/s2/relocwho.py`, from the original's .text relocations): only `_output`
(FUN_1000c670, through 0x10015398 = table - 0x20 for the class and 0x100153b8 for the state), and in the rebuild
`_output` is the host's vsprintf (build/overrides.c); Im_MixerInit reads the doubles just below (0x10015378..0x100153b0).
No instruction of the rebuilt imuse.dll refers to 0x10015398..0x10015430 (objdump).  So the false pointer had no effect at
run time; fixed anyway, the data image should hold the original bytes: `names/data_relocs.json` gets an IMUSE.DLL entry
with `not_pointers: ["100153c4"]`.  After: 267 / 0 / 0; the linked imuse.dll differs from the one before only in those 4
bytes of .data and the .reloc section (one entry less); .text, .rdata, .edata identical.  (LUA.DLL has the same table at
0x10023ea0; gendata.py already writes its 0x10020600 as a plain `.long 0x10020600`, "code address, not a function start",
so the bytes are the original's there.)

**LUA.DLL, 68 missed** (r2's statement confirmed and narrowed down): the slots are 0x1002974e..0x1002984a (64 entries) and
0x1002989a..0x100298a6 (4), unaligned, all values code addresses inside FUN_10019bfa (64 + 0), FUN_1001a7ac (2) and
FUN_10018d14 (2), which are MSVC's x87 transcendental / exception helpers; the tables are referenced by the original only
from FUN_10019bfa (0x1002974e, its jump table) and FUN_1001a7ac (0x10029882 / 0x1002986e; the 4 slots are entries 6..9 of
the table at 0x10029882).  All three functions are `lib_replace` "dead" in the rebuild (trap stubs), and no instruction of
the rebuilt lua.dll refers to 0x10029700..0x100298bf.  The bytes stay the original values (plain numbers), which nothing
reads; no relocation needed.  CHORE.DLL: nothing to do.
