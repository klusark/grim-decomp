# s1: the intermittent clean-room crash in save_load (round s, 2026-11-09)

## Symptom

`run.py decomp` crashed now and then in save_load (the first `Load()` of the suite): an access violation at
`ResRef_Remove+9` reading `*ref` with `ref == NULL` (EAX = 0x4c444d4d "MMDL" is the tag FUN_10004d70 just pushed, not
data read as a pointer), called from `ModelComponent_Destroy` <- CHORE.DLL `FUN_10004d70` <- `FUN_10004c70` <-
`Cos_Free` <- `Cos_Restore` <- `Engine_LoadGame`. Every report has ECX = 0x21: the costume handle 0x21 (slot index 32).

## Reproduction

`--only save_load` never crashes because the state comes from the 39 test files before save.lua. A private harness
(scratchpad `repro.py`: imports grim_tools/cleanroom/run.py read-only, points its build / run folders at
`C:\Users\Joel\grims1\w<slot>`, its own GRIM_MULTI tag, runs the whole suite and stops the game at `save_data_none`)
reproduced it with the unchanged build: **7 crashes in 16 runs** (two or three games at once; four at once fail
earlier with a DirectDraw error, and a run folder under the long scratchpad path overflows a path buffer, hence the
short folder). All seven: the same address, handle 0x21.

## Root cause (CHORE.DLL slot allocator, a latent bug of the original)

`FUN_10004e50` hands out a costume slot (table 0x100143b4 of 0x3c-byte records, +0x38 = 1 when free, size 0x100143b0,
"in use" count 0x100143ac). When no slot is free and `count + 1 > size` it reallocs the table 8 records bigger, marks the
records **from the count** (not from the old size) up to the new size free and returns the record at the count. The
original's machine code does exactly this (objdump of CHORE.DLL 0x10004e50; `FUN_10005090`, the instance records, the
same). The count is not the number of slots in use: `Cos_Load` does not lower it when a costume fails to load
(0x10001748: `FUN_10004c70` marks the slot free, the count stays).

In the suite, `actor_attrs.lua` calls `LoadCostume("no_such.cos")`: the count becomes one more than the slots in use.
When the table later grows from 32 to 40 (the 33rd costume, `x_spot.cos` of `LightMgrStartup`), the count is 33, so
records 33..39 are marked free, 33 is returned, and **record 32 (handle 0x21) keeps the bytes of the reallocated block**
(stdMemory_Realloc = alloc + copy of the old 32 records + free). Logged at the growth (debug build, every run):
`grow old=32 used=33 new=40`, record 32: `f38=fffffffe n=fffffffe comps=08525f44`, `f38=322c3131 ...`, `f38=00000005
n=10516e5c ...`, all zeros in other runs: whatever the heap returned. +0x38 == 0 makes it a costume **in use**; with
zeros it is an empty one (harmless; the dump at Engine_LoadGame showed handle 0x21 in use with 0 components in good
runs), with a stale block it is a costume with a stale component count / array. `Cos_Restore` frees every costume in
use, so the first `Load()` runs the component destructors over that stale array: in the crash reports the "component
record" is a live 0x30-byte chore table of Cos_CreateCosInstance (records {0,i,0}; stdMemory header Costume.c line
0x347 next to it), type index 0 = MMDL, data NULL -> ResRef_Remove(NULL). The other reported crash (inside a system DLL
under Surface_Unlock in Render_DrawProgressBar during Engine_LoadGame) fits the same cause: Cos_Free also passes the
stale pointers to stdMemory_Free (no magic check in this build), corrupting the heap, and the progress bar at 0.3 is
drawn right after Cos_Restore.

Why the original never showed it and the rebuilt exe does intermittently: which block the realloc gets, and what it
held, depends on the heap (the host msvcrt heap here, the bundled MSVC CRT heap in the original) and on the
allocations of the other threads (iMUSE real-time timer, sound): more load / other game processes changed how often the
block held a zero at +0x38 (0 to 50 % of the runs). The original's runs only worked because the bytes there happened to
be non-zero ("free").

Ruled out on the way: a GRIM_FENCE-style build with page-fenced, never-reused blocks for every CHORE.DLL allocation
(debug only, not committed) never faulted - no use after free of a costume array; the stale pointer is uninitialised
memory, not a freed costume's.

## Fix

`build/overrides_s1_chore.c`: FUN_10004e50 and FUN_10005090 in C, the original's with the new records marked free
**from the old size** (the ones below the count were undefined in the original) and the table grown in steps of 8 until
the returned record is inside it (the original grows once and writes past the end after more than 8 failed loads).
The returned record, and so every handle, the counts, the realloc size and the records below the old size are the
original's.

## Verification

* Differential test against the original machine code (`build/difftest/s1/`: `slice.py` cuts the two functions out of
  the install's CHORE.DLL and relocates their 15 data references each; `build.sh`, `s1_test.exe [cases] [seed]`):
  1,000,000 random states (sizes 0..64, counts up to size + 7, random free flags and record bytes; a mock realloc whose
  added part is random): **0 differences** when the added records read as free (the case where the original is
  defined), at -O0 and -O2; with a zeroed added part the original left 205,548 undefined records "in use", the override
  0. `mutate.sh`: 7 of 7 mutants caught.
* Harness with the fixed build (two games at once, same as the baseline): **0 crashes in 32 runs** (baseline without
  the fix: 7 in 16).
* Clean-room suite (`GRIM_DECOMP=<worktree>/build/run run.py decomp`), **12 full runs in a row**, each one engine run
  (no crash restart) and `0 of 5107 tests differ, 0 are close (within 0.001), 5107 the same`; 8 of the 12 ran while
  the harness kept two more games running (load).
* `make -C build` / `link`: the stub lists of CHORE.DLL and the EXE are the same as the base build's.
