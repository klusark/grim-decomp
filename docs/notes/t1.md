# t1: whole-game autorun fails in ch54_thunderboys (2026-11-09)

Result: **not an engine fault.** The original v1.01 exe, from the same checkpoint (grim54.gsv) and with the same autorun
(the one the save holds), walks Manny exactly as the rebuilt engine does and fails with the same line:
`AUTORUN FAIL nav: no way from 0.78 -0.35 to -0.24 -0.07 in sewer hub for 18 seconds`. The failure is autorun drift.
No source change.

## Evidence

Per-frame probe (Manny's x, y, yaw and GetActorSector(manny, HOT) every frame for 2400 frames from the start of the
chapter), on both engines from grim54.gsv (grimW_work/ck), both at 17 ms frames:

* rebuilt (this worktree's build of 88c9c55): `C:\Users\Joel\grimT1_work\r_t1a_dbg.log`
* original (install's clean exe + grimlaunch/patch.dll): `C:\Users\Joel\grimT1_work\orig54e.log`

The sequences of distinct (x, y, yaw) states are identical, 310 of 310, to the 4 printed decimals
(`grimT1_work/*.pos`, `diff` empty). Both walks stop at (0.7837, -0.4556) yaw -3564.08, then (0.8841, -0.5214), then
(0.7766, -0.3484) yaw -3565.17; HOT stays nil on both; both end with the same AUTORUN FAIL line.

## Why Manny stops short of the ladder box (the autorun)

* The game's climb starts when Doorman sees GetActorSector(manny, HOT) = `ladderup_box` (sh.set: (0.39,-0.32)
  (0.67,-0.89) (0.69,0.80) (0.33,0.26), z 0, height 0.30). At y = -0.456 it spans x 0.46 .. 0.675.
* The autorun walks "into the sector of /shtx010/" with `AR_GOAL_REGION`: `ar_nav_door_hot` takes every hot sector whose
  set entry is the door object, and sh.lua maps both `sh.ladderup_box` and `sh.ladderdn_box` to `sh.te_ladder`. So the
  goal list also holds `ladderdn_box`, the box at the top of the ladder (z 2.95: (0.14,0.63) (0.16,-0.84) (0.79,-0.78)
  (0.78,0.63)).
* `ar_follow_progress` ends the walk as soon as `ar_w_in_goal_hot(nav, x, y)` is true, and that test is 2-D (no height;
  `ar_w_hot_zok` exists but is not used there). The footprint of the upper `ladderdn_box` reaches x = 0.7877 at
  y = -0.456 and 0.7869 at y = -0.348: Manny stops in the first frame inside it (0.7837 and 0.7766), 0.11 m before
  ladderup_box, on the floor level where the engine (correctly) reports no hot sector.
* The autorun then waits 8 s for a climb that never comes, steps out ("out of the sector of /shtx010/ first", again
  because the 2-D test says he is in it), walks back, stops at the footprint again, and the next plans find no way.
* The 2026-10-31 ScummVM pass (grim_tools/autorun/logs/ch54_thunderboys.log) stopped at the same two points (0.777 -0.448,
  0.785 -0.355); its older autorun then planned a partial way to (0.50 -0.14) without the goal region and walked into
  ladderup_box. The current autorun does not take that branch.
* So the BUILD_NOTES line "Manny enters ladderup_box but the level never changes" is not what happens: he enters the
  floor projection of ladderdn_box.

The fix belongs in grim_tools/autorun (e.g. use the height check `ar_w_hot_zok` in `ar_w_in_goal_hot`, or leave hot
sectors of another level out of `ar_nav_door_hot`); not done here (grim_tools is not to be edited).

* The install's GRIMFANDANGO.exe is now `gfupd/v101_clean.exe` (no grimdlg.dll import, so no grimdebug.log and no F12
  hook): `resume_original.sh` starts a game that never logs (also the empty logs of 2026-11-07 in autorun/logs).
  `gfupd/v101_fl.exe` in a run folder of its own (what `orig_run_folder.sh` does; that script has never been run) exited
  at once with code 0.
* What worked: a private run folder `C:\Users\Joel\grimT1_orig` (the install's clean exe and DLLs, data hard-linked,
  grim.ini with GrimDataDir = the folder) started by grimlaunch.exe with a private patch.dll built from a copy of
  `grim_tools/launcher/patch.c` with `installHook()` enabled (the grimrun.lua runner, commented out in the original
  source) and `doFile("grimrun.lua.ran")` relative. The file must have CRLF line ends: an LF-only file runs nothing and
  lua_dofile still returns 0. Script: `C:\Users\Joel\grimT1_work\orig_t1.sh <tag>` (`PROBE=<lua file>`, `SLOT=<n>`),
  sources `grimT1_work/patch.c`, `config.c`. grimlaunch's default patches give the simtime 17 ms frames, so the
  original's frames are the rebuilt's (GRIM_SIMTIME=17).
* Nothing in C:\GOG Games\GRIMDATA was changed in the end: one attempt with resume_original.sh rewrote grimpatch.bin
  (restored with mk_grimpatch.py, same 97 bytes) and emptied grimdebug.log (empty before), and a copied grim54.gsv was
  removed again. Rebuilt runs used a private data copy `C:\Users\Joel\grimT1_data`.
