# Round s3: the SEH strip rule, and movie sound before / after the step-table fix (2026-11-09)

Two follow-ups of round r2 (docs/notes/r2.md): (1) `tools/build_src.py`'s `seh_strip` rule missed ObjectState_Construct,
which r2 worked around with a declining handler in build/overrides_r2.c; (2) the effect on movie sound of r2's data-image
fix (the VIMA step table 0x004daa58 held relocated addresses in entries 22-31 before 6da2d60) was never measured.

## 1. SEH frames: the strip rule

### Why the rule missed it

`strip_seh_frames` runs on Ghidra's raw text (inside `fix_ftol`, before `frame_locals` turns the locals into `#define`s; the
`#define` form seen in `src/` is only what is printed at the end). It failed on two shapes of the raw text:

* **The state slot updated through its low byte.** ObjectState_Construct writes the C++ unwind state as
  `local_4 = CONCAT31(local_4._1_3_,1);` (the original's `mov byte [ebp-4], 1`). The rule only dropped `state = <const>;`,
  so `local_4` stayed in use and the rule gave up on the whole function: the compiled C kept
  `fs:[0] = &local_c` / `fs:[0] = local_c`, a live SEH registration whose handler (the thunk FUN_004d60e9) was
  the decompiled `__CxxFrameHandler()` without its FuncInfo in EAX.
* **Handler and state stored after `prev = fs:[0]`.** The rule looked for the `state = 0xffffffff` and `handler = FUN_..`
  stores only in the four lines before `prev = *unaff_FS_OFFSET`. In Actor_CreateWalker, ObjectState_Create and
  ObjectState_Destruct, MSVC ordered them after it (`local_c = fs:[0]; local_4 = -1; pcStack_8 = FUN_..; fs:[0] = &local_c`),
  and a destructor starts in state 0, not -1. The fs:[0] lines were removed, but the dead stores of the handler address
  and the state stayed (Actor_CreateWalker's store of FUN_004d605b to its frame survived into the linked exe).

### The fix (tools/build_src.py, `strip_seh_frames`)

* The registration block is from 4 lines before the first of `prev = fs:[0]` / `fs:[0] = &prev` to one line after the
  second; the handler and the state are looked for anywhere in it. The state is the `X = 0xffffffff` store, or else
  (a destructor) a `<name>_4 = <const>` store after the registration: Ghidra's name for the slot [EBP-4].
* State changes that are dropped: `state = <const>;`, `state._0_1_ = <const>;`, `state = CONCAT31(state._1_3_,<const>);`.
* Unchanged: the frame is only removed when all its variables are dead afterwards (otherwise the text is left as it was),
  and only for the functions `names/seh_strip*.json` lists.

`git diff src` after `rm -f src/*/*.[ch] src/*/*.md && python -I tools/build_src.py` touches only those functions:

### The handler thunks and r2's workaround

With the stores gone, nothing references any of the `mov eax, FuncInfo; jmp __CxxFrameHandler` thunks: no object (nm),
no instruction, no data-image slot (`grep` of data.s). They are now `names/lib_replace.json` "dead" like r2's funclets:
EXE 004d6046, 004d605b, 004d607b, 004d60ba, 004d60e9, 004d610b; LUA.DLL 10021fa6, 10021fbb, 10021fe6, 10021ffb,
1002201b, 1002203b, 1002205b and FUN_1000f0e0 (the LUA.DLL handler body, `__InternalCxxFrameHandler(.., EAX = FuncInfo)`,
which only those thunks called). **r2's FUN_004d60e9 in build/overrides_r2.c is removed**: nothing registers it.
Stub counts are unchanged (EXE 42, LUA.DLL 58): nothing references the dead symbols, so no trap stub is needed.

## 2. Movie sound

### What decodes it

Grim's SNM movies carry their sound in `Wave` chunks (one per frame, the first carries ~3.3 s ahead), VIMA compressed. The
codec is the module "LECMODULE insane_wave flobdec" (FUN_004cba30 registers it, FUN_004cbbb0 = 'Wave'): FUN_004cbc00 parses
the chunk header (sample count, an optional 0xffffffff stream id, per channel the step index byte and the predictor), writes
a sound header into the 500000-byte buffer PTR_008da4f0, decodes the samples with FUN_004cbf50 and hands the buffer to the
SOUND service (`(*UINT_008da4ec)[0](buf, -1, 0x7f, 0, 0x40)`). FUN_004cbf50 builds the 89 x 64 table DAT_008d7868 from the
step table DAT_004daa58 on first use and reads DAT_004daa58 directly as well. Both functions are compiled decompiled C
(crt_unnamed.c) in every build; neither was ever assembled, so the original machine code is the original exe itself.

### Test: build/difftest/s3/vimadiff.c, moviesound.py

`vimadiff.exe` maps a program image (the original `C:\GOG Games\GRIMDATA\GRIMFANDANGO.exe`, or a rebuilt grimfandango.exe)
at its preferred base 0x400000 in a child process (reserved while the child is suspended; the harness is linked at
0x30000000 with a 512 KiB stack so that its own stack is placed below 0x400000), without imports (every IAT slot points at
a function that exits: the codec calls none) or start-up code, points UINT_008da4ec at a recording callback and
PTR_008da4f0 at a buffer, sets UINT_008d7860 from the movie's FLHD Wave entry, then calls FUN_004cbc00 on every Wave chunk
of the movie in order (the codec's predictor / step index state carries over between chunks, as in the game). For a rebuilt
image the addresses come from nm (`_FUN_004cbc00`, `_UINT_008da4ec`, `_PTR_008da4f0`, `_UINT_008d7860`).
`moviesound.py` extracts the Wave chunks of each movie, runs the original and each rebuilt image and compares the buffers
handed to the SOUND service: the header (0x36 bytes for the first chunk of a stream, 0x12 after), the 16-bit PCM and the
return values.

Images: 85dd22f and 6da2d60 built from `git archive` of each revision with the usual procedure (scratch directories), and
this round's build (s3). Movies (tools/lab.py extract from MOVIE00-04.LAB): intro, falling, stocking, mo_ts, eatbird, eleup,
thepearl, cam_cyc (silent); the other 15 of MOVIE00.LAB have no Wave chunks.

* **85dd22f's movie sound was badly wrong**: whenever the step index of a loud passage reached 22-31, the next sample
  jumped by tens of thousands and the decoder's predictor ran into the clamp; about half of all differing samples are
  pinned at +32767 / -32768 (the original's output never clips on these movies). The error energy over the whole movie is

  and the headers and return values were always right.
* **6da2d60 is identical to the original** on all 8 movies (headers, every PCM sample, return values), and so is this
  round's build. Nothing left to fix here.

### Not movie sound, found on the way

relocheck's one false IMUSE.DLL pointer (0x100153c4, r2 notes) is inside the C runtime's printf state table
`_UNK_100153b8` (bytes 0,6,2,16 -> `_sect_data + 0x9600`). Its only user, the decompiled `_output` FUN_1000c670, is replaced
by the hand-written version in build/overrides.c, so nothing in the rebuild reads it. Left as it is.
